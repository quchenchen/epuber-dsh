# 能力中心 · 企业化部署规划

> 本文是 `DESIGN.md` 的落地计划。设计已经定：**不新建平台**，以 `iflytek/skillhub` 为底座私有化部署，  
> 客户端侧已经实现为技能插件里的「SkillHub」页签（见 `DESIGN.md` §8）。  
> 这里只回答一个问题：**怎么把它变成企业内网里别人能用的服务。**

## 0. 目标与非目标

|      | 内容                                                    |
| ---- | ----------------------------------------------------- |
| 目标   | 内网可访问的技能中心；成员在桌面端浏览、安装受控版本的技能；发布与下架有审批与审计；身份来自企业现有体系  |
| 非目标  | 不接管 MCP/tool（二期）、不做「装了什么」的终端资产盘点、不替代企业 IdP            |
| 成功判据 | 新成员从「拿到客户端」到「装上第一个受控技能」不需要命令行、不需要问人；任一技能版本可追溯到发布人与审批人 |

---

## 1. 部署单元与拓扑

一套实例四个容器（`compose.release.yml`），加一个反向代理：

```
浏览器 / 桌面端
      │  HTTPS 443
   [ 反代 Nginx/Traefik ]            ← 唯一对外暴露面
      ├─ /            → web:3000     (React 控制台)
      └─ /api         → server:8080  (REST + 下载)
                       ├─ postgres:5432   （元数据、审计、版本）
                       ├─ redis:6379      （会话、限流、缓存）
                       ├─ minio/S3        （技能包制品）
                       └─ skill-scanner   （包安全扫描，随 server 启动）
```

**硬规则**：`server`、`postgres`、`redis`、`minio` **一律不做宿主端口映射**。本地开发那套 `15432:5432`、`8080:8080` 的写法不能进生产 compose。

**唯一出口**：桌面端只需要 `https://skillhub.<内网域名>`。它不出外网、不调用任何第三方地址。

## 2. 环境划分

| 环境      | 用途              | 数据     | 谁能进         |
| ------- | --------------- | ------ | ----------- |
| dev     | 本机 compose（已在跑） | 丢弃随意   | 我们          |
| staging | 升级预演、包格式与权限回归   | 生产脱敏快照 | 我们 + 试点部门代表 |
| prod    | 正式              | 正式     | 全公司按命名空间授权  |

**升级必须先过 staging**：SkillHub 是外部项目，任何版本跳动都可能改 schema 或改包协议。

---

## 3. 容量与规格

按 2000 名成员、50 个命名空间、日均 500 次安装估算（技能包平均 200 KB）：

| 项        | 最小可用（≤300 人）   | 推荐（≤2000 人）                     |
| -------- | -------------- | ------------------------------- |
| server   | 2C / 4G × 1    | 4C / 8G × 2（无状态，可横扩）            |
| postgres | 2C / 4G / 100G | 4C / 16G / 500G SSD，日备 + WAL 归档 |
| redis    | 1C / 2G        | 2C / 4G                         |
| 对象存储     | 本地卷 100G       | MinIO 4 盘或企业 S3，开版本化            |
| 反代       | 与 server 同机    | 独立，终结 TLS                       |

> 技能包是**小文件**：真正吃容量的是历史版本保留。策略：每个技能保留最近 20 个版本 + 所有 `stable` 标签版本，其余归档到冷存储（不要删，审计要查）。

## 4. 配置与密钥

必须外部化的项（本地 `.env.release` 里的这些都算）：

| 变量                                     | 说明                  | 生产做法                       |
| -------------------------------------- | ------------------- | -------------------------- |
| `SKILLHUB_PUBLIC_BASE_URL`             | 对外地址，影响下载链接与 cookie | 写域名，不写 IP                  |
| `POSTGRES_PASSWORD`                    | 数据库口令               | 密钥管理系统注入                   |
| `SKILLHUB_STORAGE_S3_SECRET_KEY`       | 对象存储密钥              | 密钥管理系统注入，不给运维个人持有          |
| `SKILLHUB_DOWNLOAD_ANON_COOKIE_SECRET` | 匿名下载 cookie 签名      | 随机 32 字节，重建即失效             |
| `BOOTSTRAP_ADMIN_PASSWORD`             | 首个管理员               | **首次登录后立即改密并停用 bootstrap** |

**三条纪律**：

1. 镜像 tag **必须钉死版本号**，禁止 `latest`。当前本地用的是 `SKILLHUB_VERSION=latest`，只为验证方便。
2. `docker compose config-hash` 不含 `env_file` 内容——改了 `.env` 必须 `--force-recreate`，否则你以为改了其实没生效。
3. 任何令牌（`sk_…`）不进 git、不进聊天记录、不进工单。它们只存在于 SkillHub 库里（哈希）与成员本机凭据存储。

## 5. 网络与接入

- **域名**：`skillhub.<内网域名>`，证书走企业内部 CA；桌面端需要信任该 CA（见 §8）。
- **反代必须传的 header**：`X-Forwarded-For`、`X-Forwarded-Proto`；否则限流按反代 IP 计数，会误伤全公司。
- **上传与下载体积**：默认上限足够技能包（≤50 MiB），但反代要显式放开 `client_max_body_size`，否则发布大包会 413。
- **CSRF**：`POST /api/v1/auth/*`、`POST /api/v1/tokens` 需要 `X-XSRF-TOKEN`（取自 `XSRF-TOKEN` cookie）。桌面端不直接调这些接口，令牌由平台侧签发后下发（见 §8），因此不要为此在客户端开源码。
- **出网**：SkillHub 不需要外网。若接了 GitHub 同步源，单独放行，并在此处标注它是唯一出网点。

## 6. 存储与备份

| 对象                             | 方式              | 频率        | RPO   | RTO    |
| ------------------------------ | --------------- | --------- | ----- | ------ |
| Postgres                       | 每日逻辑备份 + WAL 归档 | 日备 / 连续归档 | ≤5 分钟 | ≤2 小时  |
| 对象存储                           | 版本化 + 跨机复制      | 实时        | ≈0    | ≤1 小时  |
| 配置（`.env`、compose、Helm values） | 独立配置仓库，加密       | 每次变更      | —     | ≤30 分钟 |

**恢复演练**：上线前做一次「删库 → 从备份恢复 → 校验技能包可下载」，没有演练记录的备份等于没有备份。

## 7. 身份与部门（部署前必须定的一条）

两条路线在 `DESIGN.md` §2.2 已列出，这里给出可执行差异：

|        | A. 命名空间映射                                         | B. SSO 对接                                                       |
| ------ | ------------------------------------------------- | --------------------------------------------------------------- |
| 实施     | SkillHub 用自带账户；建一张 `部门 → 命名空间` 映射表，成员由管理员批量加入命名空间 | 按 `docs/12-private-sso-integration-playbook.md` 接企业 IdP，成员免二次登录 |
| 成员体验   | 需登录一次 SkillHub（Web 或桌面端填一次令牌）                     | 无感                                                              |
| 我们的工作量 | 一张映射表 + 批量开通脚本（1–2 人日）                            | 改它的鉴权扩展并跟随上游升级（≥1 人周，含回归）                                       |
| 风险     | 两套账号，离职需两处停用                                      | 上游改扩展点会让我们的补丁失效                                                 |

**建议**：先 A 上线，同时把「成员离职需停用」加进运维 checklist；等成员规模或合规要求逼上来再评估 B。**不要两条都做**。

**权限矩阵（A 路线）**：

| 角色    | 命名空间    | 能做什么             |
| ----- | ------- | ---------------- |
| 平台管理员 | 全部      | 建命名空间、全局推广审批、看审计 |
| 部门管理员 | 本部门     | 审核本部门包、上下架、管成员   |
| 成员    | 被授权命名空间 | 搜索、安装、查看版本历史     |
| 只读审计  | 全部（只读）  | 导出审计与下载记录        |

|                                       |                                        |
| ------------------------------------- | -------------------------------------- |
| 部门层级：现有 \`Organization(kind: personal | team)\` 是扁平的，部门树在映射表里维护，**不回写既有身份模型**。 |

## 8. 客户端接入

已实现的接入点（`packages/plugins/skills`）：

| 项      | 机制                                                                                                |
| ------ | ------------------------------------------------------------------------------------------------- |
| 服务地址   | 优先读已保存配置；未配置时读 `EPUBERDSH_SKILLHUB_URL`（也可用插件 `config.registryUrl` 注入），出厂默认 `http://127.0.0.1:8080` |
| 默认命名空间 | `EPUBERDSH_SKILLHUB_NAMESPACE`，默认 `epuberdsh`（旧名 `epuberdsh` 视为过期默认值，会自动跟随）                           |
| 令牌变量名  | `EPUBERDSH_SKILLHUB_CREDENTIAL`，默认 `SKILLHUB_TOKEN`；**值**存在平台凭据存储，不落明文                              |
| 成员手填   | 「技能市场 → SkillHub → 连接设置」，仅在没有部署默认值时出现                                                             |

部署时要做的事：

1. 打包镜像/安装包时注入 `EPUBERDSH_SKILLHUB_URL=https://skillhub.<内网域名>`，成员就不必填地址。
2. 令牌发放二选一：**平台预置**（把令牌写进凭据存储，成员零操作，但一个令牌全公司共用，审计只能定位到「平台」）或**按人签发**（成员首次使用时粘贴自己的令牌，审计能定位到人）。企业合规要求「谁装了哪个技能」可追溯时，必须按人签发。
3. 内网 CA 要预置到系统信任链，否则面板会报「无法连接技能中心服务」——这个报错文案是刻意模糊的，避免把证书细节暴露给终端用户。
4. 内置技能进库用 `packages/plugins/skills/scripts/publish-builtin-skills.mjs`：它按内容哈希跳过未变的技能，因此重复执行不会刷版本；注册中心对发布会限流，脚本已带退避重试。

## 9. 升级与回滚

顺序固定，不要跳步：

```
staging 起新版本 → 跑包格式/权限/下载回归 → 备份 prod（DB+对象存储）
→ 停写（可选，维护窗口）→ 起新 server（自动迁移）→ 起新 web
→ 冒烟：登录 / 搜索 / 下载 / 安装 / 审计可查 → 观察 30 分钟
```

回滚条件与动作：**任何一步冒烟失败，立刻回滚镜像 tag**；如果迁移已经改表，回滚要同时恢复 DB 备份，不能只回镜像。所以**迁移前必须确认备份可恢复**。

同时固定一条：**客户端不跟 SkillHub 同步升级**。面板只依赖 REST 契约，SkillHub 升版不需要发新版客户端；如果某次升级改了契约，那是我们要提前在 staging 抓到的回归项。

## 10. 可观测性

| 指标        | 告警阈值          | 为什么看它             |
| --------- | ------------- | ----------------- |
| `5xx` 比例  | >1% 持续 5 分钟   | 契约或依赖出问题          |
| 下载失败率     | >2%           | 存储或权限配置错，成员装不上    |
| p95 搜索延迟  | >800 ms       | 索引或 DB 压力         |
| DB 连接数    | >80% 上限       | 泄漏或连接池配置错         |
| Redis 内存  | >80%          | 会话与限流会一起失效        |
| 扫描任务积压    | >50 条持续 10 分钟 | 发布会被卡住，作者以为发了其实没有 |
| 磁盘/对象存储增长 | 周增 >20%       | 版本保留策略没生效         |

日志：应用日志进集中日志系统，**审计日志单独导出**（谁、何时、对哪个技能版本做了什么），保留 ≥180 天。

## 11. 安全

1. **镜像与依赖**：镜像来自官方发布并固定版本；上线前跑一次 CVE 扫描，高危阻断。
2. **越权测试**（上 staging 必做）：部门 A 成员能否在搜索里看到部门 B 的私有包？能否用直链绕过可见性下载？两项都要以「看不到 / 403」为通过。
3. **限流**：下载与搜索是公开可枚举的入口，反代层再加一道按 IP 的限流，不要只依赖应用内 `@RateLimit`。
4. **令牌治理**：令牌可撤销、可过期；离职流程里必须有「撤销 SkillHub 令牌」一步（A 路线下还要停用账号）。
5. **不做的事**：不在客户端缓存令牌明文、不把令牌写进日志、不在 URL 里带令牌。

## 13. 验收清单（可测）

1. 从一台**未装过任何配置**的内网机器，新成员登录桌面端 → 打开技能市场 → SkillHub 页签 → 不填任何地址即可看到技能列表。
2. 安装一个技能后，`~/.dsh/skills/<name>/SKILL.md` 存在，且对话里能触发它。
3. 部门 A 的成员搜索不到部门 B 命名空间的包；用直链下载返回 403。
4. 某技能发布 v2 后，控制台版本历史可查；审计日志能查到「谁在何时提交、谁审批、谁安装」。
5. 反代后成员真实 IP 出现在限流与审计里（不是反代 IP）。
6. 杀库 → 从备份恢复 → 技能仍可下载安装；恢复耗时记录在案。
7. 客户端令牌不出现在任何项目文件、日志与进程参数里。

## 14. 风险与未决

| 风险              | 影响            | 处理                                                |
| --------------- | ------------- | ------------------------------------------------- |
| A 路线两套账号，离职只停一处 | 离职成员仍可安装技能    | 把「撤销 SkillHub 账号/令牌」写进离职 checklist；P2 评估 B        |
| 共用令牌            | 审计无法定位到人      | 合规要求人级追溯时必须按人签发                                   |
| 上游升级改契约或 schema | 客户端 500 或安装失败 | staging 回归 + 客户端只依赖 REST 契约，不 import 它的模型         |
| 版本历史无限增长        | 存储成本          | P2 定保留策略：最近 20 版 + 所有 `stable`                    |
| 尚未验证的规模上限       | 大并发下载打满带宽     | 下载走对象存储直链或加 CDN，不要全部经 server 转发（需在 staging 压测后确认） |

## 15. 已部署实例（2026-11-02）

第一套生产实例已经上线，接入点是 **`https://skill.igeewa.com`**。以下都是实测值，不是计划值。

### 15.1 主机与位置

| 项 | 值 |
| --- | --- |
| 主机 | `39.98.114.52`（阿里云，Alibaba Cloud Linux 3，x86_64，4 vCPU / 15 GiB） |
| 部署目录 | **`/media/web3x/skillhub`**（80 G 数据盘，剩余 64 G） |
| 数据卷 | `/media/web3x/skillhub/data/{postgres,redis,storage}`，由 `docker-compose.override.yml` 绑定；根盘只剩 7 G，绝不能把库写在 `/var/lib/docker/volumes` |
| 反代 | 复用面板既有 nginx（`/www/server/nginx`），站点文件 `/www/server/panel/vhost/nginx/skill.igeewa.com.conf` |
| 证书 | 复用既有泛域名 `*.igeewa.com`（`/www/server/panel/vhost/cert/igeewa.com/`，2027-01-06 到期），未新签证书 |

### 15.2 端口与网络

容器对外**零端口**，全部绑定回环，唯一入口是 nginx 的 443：

| 服务 | 监听 | 说明 |
| --- | --- | --- |
| web | `127.0.0.1:3000` | 控制台，nginx 反代到它 |
| server | `127.0.0.1:8080` | REST + 下载 |
| postgres | `127.0.0.1:15432` | 规避本机已有的 5432（lobe-postgres） |
| redis | `127.0.0.1:16379` | 规避本机已有的 6379（lobe-redis） |

### 15.3 与默认 compose 的三处差异

1. **`docker-compose.override.yml`**：把三个数据卷改成大盘上的绑定挂载。
2. **`SKILLHUB_STORAGE_PROVIDER=local`**：不引入 MinIO/OSS，制品落在 `data/storage`。
3. **`SKILLHUB_BUILTIN_SKILLS_ENABLED=false`**：不 seed 上游那 25 个与业务无关的公共技能；空目录由我们自己的 16 个技能填充。

镜像来源要注意：本机 `ghcr.io` 直连握手超时，实际走 `ghcr.m.daocloud.io` 拉取后 `docker tag` 回 `ghcr.io/...` 原名，compose 因此不必改。

### 15.4 初始化做了什么（可重放）

```bash
# 1) 环境变量（密钥在主机上生成，不进仓库）
cp .env.release.example .env && python3 make-env.py

# 2) 起服务
docker compose --env-file .env -f compose.release.yml -f docker-compose.override.yml up -d

# 3) 引导管理员 + 建命名空间 + 签发令牌（loopback，不走公网回环）
bash init-instance.sh '<BOOTSTRAP_ADMIN_PASSWORD>'

# 4) 发布 16 个内置技能到 epuberdsh
skillhub publish <dir> --namespace epuberdsh --visibility public \
  --registry http://127.0.0.1:8080 --token <token>
```

结果：`/api/web/skills?namespace=epuberdsh` 返回 **16 条，全部 `PUBLISHED`**；全站条目数也是 16，说明内置集确实没被 seed。

### 15.5 客户端接入

桌面端「技能市场 → 企业技能中心 → 连接设置」填：

| 字段 | 值 |
| --- | --- |
| 服务地址 | `https://skill.igeewa.com` |
| 访问令牌 | 各成员在 `https://skill.igeewa.com` 个人设置里自行签发 |
| 默认命名空间 | `epuberdsh` |

令牌是**按人**的，谁签发审计就记谁；不要把管理员的令牌发给全公司。
